## Data Source Architectural Patterns

### Table Data Gateway
One instance handles all the rows in the table.

One location for SQL; select, insert, update and deletes.
Stored Procedure.

#### How It Works
Usually stateless.

Will always return multiple items/rows.
Can return a map.
>Even a simple find-by-ID query will return multiple data
items.  
**QUESTION: Why does it return multiple items?**  

Map is a solution to handle multiple return; but destroys type checking.
Use [`Data Transfer Object`](#data-transfer-object).
Or return Record Set - but that makes it hard to substitute with non-database integrations.

Where [`Record Sets`](#record-sets) are used,
it's nice to combine with [`Table Module`](#table-module).

>If all of your updates are done through the Table Data Gate-
way, the returned data can be based on views rather than on the actual tables,
which reduces the coupling between your code and the database.  
**QUESTION: Why so?**

With domain model; returning Domain Object - which creates bidirectional 
dependencies between Domain Objects and the Gateway.  
**[QUESTION: Why can it not return domain objects without the object knowing**
**about the Gateway?]**

Simple cases can have one for all tables 
Often it is one for each table, and maybe even one for interesting queries.
When these queries are based on views, it's hard to update - but this abstraction
makes it easier to update the underlying tables.

#### When to Use It
Decision:
1. Use a Gateway?
2. Use Table or Row?

Mappping to database table or record type is nice, which makes it simple.

Not often used with [`Domain Model`](#domain-model),
as [`Data Mapper`](#data-mapper) isolates better.  
Works well with [`Table Module`](#tabel-module), which is better than
[`Row Data Gateway`](#row-data-gateway) in those cases; ie. there is 
[`Record Set`](#record-set) support. This also goes for 
[`Transcation Script`](#transaction-script); and one goes for Row Data Gateway
when there is no good support for Record Sets.

Can use with Data Mappers in cases where you want to use metadata mapping
from the database, but convert from Record Sets to Domain Object manually.

Benefits with SQL and Stored Procedures is that the Gateway can encapsulate 
using both in one class.

### Row Data Gateway
Represent database rows exactly as in-memory objects.  
Hiding details of how they are accessed

#### How It Works
One-to-one with record.  
Converts in-memory types to SQL types.  
Works well with transaction scripts.  

Static Find methods, or prefered separate Finder objects.  
[C: Easier to test]

Similar to [Active Record](#active-record), only without domain logic.  

Can be used with view or query as well, updating is hard though.  

Tedious to write, but matches good with [Metadata Mapping](#metadata-mapping)

#### When to Use It
Two-stepped decision for using Row Data Gateway:
1. Gateway at all? 
2. Row or Table?

Combines good with [Transaction Scripts](#transaction-script), not with [Domain Model](#domain-model).
[Active Record](#active-record) is a better alternative if the mapping is simple. 
If mapping becomes complex [Data Mapper](#data-mapper) is preffered.

> I don’t use a Row Data Gateway when I’m using a Domain Model (116). If
the mapping is simple, Active Record (160) does the same job without an addi-
tional layer of code. If the mapping is complex, Data Mapper (165) works bet-
ter, as it’s better at decoupling the data structure from the domain objects
because the domain objects don’t need to know the layout of the database. Of
course, you can use the Row Data Gateway to shield the domain objects from 
the database structure. That’s a good thing if you’re changing the database
structure when using Row Data Gateway and you don’t want to change the
domain logic. However, doing this on a large scale leads you to three data rep-
resentations: one in the business logic, one in the Row Data Gateway, and one
in the database—and that’s one too many. For that reason I usually have Row
Data Gateways that mirror the database structure.

Using [Transaction Scripts](#transaction-script); one can isolate business logic for the object, which slowly transitions it into an [Active Record](#active-record)

### Active Record
Encapsulate database access with domain logic!
Data & Behaviour -> Most obvious approach.

#### How It Works
A [`Domain Model`](#domain-model) which match closely with DB relation.
A Row Data Gateway + Business Logic?

Consider [`Foreign Key Mapping`](#foreign-key-mapping).
Works on views and tables!

It usually has the following methods:
- Construct a new `Active Record`
- Construct `Active Record` from query result set
- Public Static Finder methods 
- Update and Inserts methods
- Getters and Setters for fields (Can be more complex!)
- **Business Logic Methods!**

> Also, if you ask for
a related table, the getting method can return the appropriate Active Record,
even if you aren’t using Identity Field (216) on the data structure (by doing a
lookup)  
**QUESTION: What does he mean here?** 

Does not hide a relational database.
Usually has more static finder methods - but doesnt need to!

Very similar [`Row Data Gateway`](#row-data-gateway).

#### When to Use It
A good choice for simple Domain Logic. CRUD.

>Derivations and validations based on a sin-
gle record work well in this structure   
**QUERSTION:What does he mean?**

For initial  [`Domain Model`](#domain-model), it is a nice choice (compete with Data Mapper).
Work only when there is an isomorphic schema correlation between them and the database.

Complex business logic -> Object direct relationship, collections, inheritance ++ ; 
which is not good with Active Record -> Data Mapper

Couples Object Design to Database Design.

Very good match with Transaction Script, especially gradually transition into when 
Transaction Script is used with Row Data Gateway

### Data Mapper
Different mechanisms for structure in DB and Objects.
Schemas might match up.

Transfer between schemas -> can become a complexity.
Failing to separate concern can have rippeling effects.

`Data Mapper` separates the object schema with the database schema, 
isolating them from each other 

Objects don't know there is a database present. 
The `Domain Model` only knows about a `Mapper`, leaving the `Domain Model` agnostic to the
persistance implementation layer!

#### How It Works

Separation of Domain and Data Source! But many implementations.
> **REFLECTION:** Entity Framework Context is an example of a `Data Mapper`?

[`Identity Map`](#identity-map) can/should be used in a `Data Mapper`!
Either a Registry or one per finder!

A `Data Mapper` is used in complex convertions or creations; e.g. collections and inheritance. 
> **COMMENT: Imaging implemenenting EF Context to generate all instances of a hierarchy with class per table!**

Transcations can be used, by organizing them in [`Unit of Work`](#unit-of-work)-pattern.

Mappers can paginate/cursor the DB, and should know when the client needs to do this!

Relations in the DB can interconnect the whole Object schema, so the mapper must again know 
when to restrict the pull. 

Or there can be used a [`Lazy Load`](#lazy-load) to fetch data when needed. 
**[Q: ASYNC LAZY LOAD?!]**. This might make the object model aware of the mapping layer.

It makes sence to split mappers up per root domain hierarchy or domain class.

###### Hadnling Finders
Object Association can load all at once or Lazy Load.
This might need to either call other find methods on the Data Mapper,
but Lazy Loading *can* avoid this.
Avoid this in simpler apps, try using `Separated Interaface`.

###### Mapping Data to Domain Fields
Data Mappers need access to the relevant fields in the object model.
Solutions: Reflection (slow but neglisable), packaging (awkward), 
public methods with context guards **[Q: How does these context guards work?]**.

Well formed objects from start? Rich constructors. 
Be aware of cyclic dependencies. Special Case code - Lazy Load. 
Or no-arg constructor - empty object, this needs true immutability

###### Metadata-Based Mappings
Decide how fields are mapped to columns in database.
Explisitt code vs [`Metadata mapping`](#metadata-mapping).
This avoids more Source Code per mapping!

#### When to Use It
Together with Domain Model, ignoring the database 
- easy testing and development of business logic!
Database Schema and Object model (you want to) evolve independently.

Downside : Extra layer.

Only with Domain Model, when Domain Model is complex and especially not under 
the developers full control!

It's complicated to build - **USE SHELFWARE!**

#### Example: A Simple Database Mapper (Java)
First example: Absurdly simple isomorphic mapping.

Using:
- `Identity Map`
- `DomainObject` super-type
- `AbstractMapper` super-type
    - Abstract find method using `Identity Map` to<> find `DomainObject`
    [COMMENT: Template methods]

1. `Find` calls `abstractFind`, casts result.
2. `abstractFind` checks Idendity Map if empty calls private template-method `load`
3. `load` rechecks Identity Map* calls `findStatement` and `doLoad` abstract "content" functions 
    and then fills the Identity Map

abstract "content" methods returns the SQL select-query-strings and builds a 
object based on result set.

Checking Identiy Map twice is due to other consumers; eg. larger query that finds a set.
The entities in the set may or may not be in the Identity map, so each entity must be checked 
when loaded.  
Eg. `findByLastName` - `loadAll` -> per returned entity `load`.

loadAll fills a list with results from each individiual call on load given a resultset.

A general method can be implemented; `findMany`- `loadAll`, 
using a new interface: `StatementSource`
> COMMENT: The `StatementSource` in the `findMany` can be simplified with 
C# Linq Expressions! This pattern is a specific pattern of a more general DDD pattern called 
`Specification`.
